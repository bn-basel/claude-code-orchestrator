A multi-agent workflow for Claude Code v1.2

Claude Code Orchestrator

One orchestrator plans with you in plain language, hands each small task to a specialised helper, proves every change by command, and opens one pull request per feature. You approve the plan and click merge. Everything in between runs on its own.

01

The loop

Twelve stages from idea to live feature. Three are yours. Work runs clockwise along the track; when a gate fails, it goes back along a siding. Small work skips the two dashed stages. Watch one feature run, or select any stage on the map below for details.

One feature running through the loop

A ticket moves from your idea through plan, plan review, your approval, tests, build, check by command, click-through, code review, pull request, merge, verify and learn. Its plan is sent back once by plan review and its build once by a failed check, then it goes clean to live. The text below the diagram describes each step.

    How to read it

    From idea to live, with three human gates

    The orchestrator (Opus 5.5) runs the loop. Helpers do the narrow jobs: write tests, write code, review, look things up. Nothing moves past a gate without proof: a passing command, a clean review, a green CI run, or your yes.

    Every failure has a defined way back, and a budget: two fixes per task, two code-review rounds and three plan-review rounds before you are asked to decide.

    Select a stage on the diagram, or use the arrow keys once one is focused.

    Stage 01 of 12

    Idea

    You

    Describe the feature in plain words. No template and no ticket format. The orchestrator turns it into a plan.

    Next: 02 Plan

    Stage 02 of 12

    Plan

    Orchestrator · Opus 5.5 · high

    • Splits the feature into small tasks. Each has a label, a list of allowed files and a Done when line that a command can check.
    • Lists every helper run in advance, plus a retry budget.
    • For wide and closed work it also writes a design check: how it fits, what it changes, and what it leaves alone.

    Comes back here when code review finds a blocker in design, or the live check fails.

    Next: 03 Plan review or, for small work, 04 Approve the plan

    Stage 03 of 12

    Plan review

    Wide and closed onlyreviewer · Opus 5.5

    A fresh reviewer reads the plan before any code exists. Mistakes are cheapest here. It checks that every file and function the plan names really exists.

    At most three rounds; it stops early once only style points remain.

    For big or closed work, the orchestrator can offer Fable as an adversarial reviewer. It only runs after your yes.

    Next: 04 Approve the plan

    Stage 04 of 12

    Approve the plan

    You

    You get a plain explanation: what changes, how it is built, how it is proven, the risks and the cost.

    Your approval covers exactly the listed helper runs, plus 2 fixes per task and 2 review rounds. Anything beyond that comes back to you.

    Next: 05 Tests first or, for small work, 06 Build

    Stage 05 of 12

    Tests first, then frozen

    Wide and closed onlytest-writer · Sonnet 5.5 · high

    A test-writer turns each Done when line into tests before the code exists. They must fail at first. Then they are frozen: the coder cannot edit them.

    Next: 06 Build

    Stage 06 of 12

    Build

    implementer · Sonnet 5.5

    • One task at a time, in an isolated worktree, inside its allowed files.
    • If anything is unclear, it stops and reports instead of guessing.
    • It commits but never pushes.

    Comes back here when the check fails, review finds a blocker in code, or CI fails.

    Next: 07 Check by command

    Stage 07 of 12

    Check by command

    Orchestrator

    The orchestrator runs commands instead of reading code. All four must hold:

    • the named tests pass;
    • the new tests fail on main, which proves they test the change;
    • only the planned files changed;
    • frozen tests are untouched.

    For work that changes a screen, ui-tester then clicks through it on the local dev server and screenshots it at phone and desktop width.

    If it fails Back to Build. At most 2 tries, then you decide.

    Next: 08 Code review

    Stage 08 of 12

    Code review

    reviewer · Opus 5.5

    The reviewer sees only the plan, the diff and the test output. It never sees the coder's own account of what it did.

    Every finding needs evidence: a command and its output, a failing test, or an input that breaks it. Without evidence it's only a note. A second round checks the fix and adds no new nits.

    Findings are ranked: blocker in code blocker in design should fix note

    Blocker in code Back to Build, for that task only, with the evidence and the scope.

    Blocker in design Back to Plan. You re-approve.

    Next: 09 Ready

    Stage 09 of 12

    Ready

    Orchestrator

    Sync with main, run the full test suite, and open one pull request. It uses the same template every time:

    WhatWhyProofReviewDatabaseFeature switchRisksHow to undo

    Then wait for CI to go green.

    If CI fails Back to Build.

    Next: 10 Merge

    Stage 10 of 12

    Merge

    You

    Apply any database migration first, then merge. Merging is deploying, so this click is the release.

    Next: 11 Verify

    Stage 11 of 12

    Verify

    Orchestrator + you

    Confirm the deploy. New customer-facing features ship behind a switch that is turned on for one customer first. You do a quick check on your phone.

    If the live check fails Switch the feature off first, then back to Plan.

    Next: 12 Learn

    Stage 12 of 12

    Learn

    Orchestrator

    Update the plan file, and propose zero to two new standing rules for your approval. Then the loop starts again with the next feature.

    02

    Where you come in

    Four moments. Everything else runs without you.

    1. 1

      Approve the plan

      One plain summary of scope, proof, risk and cost.

    2. 2

      Say yes to Fable

      Only when asked, and always with a reason.

    3. 3

      Run any migration

      Database changes stay in human hands.

    4. 4

      Click merge

      Merge is deploy. The release is your click.

    The orchestrator never relays prompts through you, and never asks you to carry messages between chats.

    04

    The helpers

    Eight files in .claude/agents/. Each does one narrow job.

    • implementer Sonnet 5.5 · high

      Codes one small task.

    • implementer-wide Sonnet 5.5 · xhigh Opus on request

      Codes one wide or closed task, checking first what depends on the code.

    • test-writer Sonnet 5.5 · high

      Writes the tests before the code.

    • reviewer Opus 5.5 · xhigh

      Reviews plans and code.

      read-only
    • reviewer-light Opus 5.5 · high

      The same review, sized for small work.

      read-only
    • adversarial-reviewer Fable 5.1

      Tries to break big work: hostile input, timing, privacy, outages, undo.

      read-onlyneeds your yes
    • ui-tester Haiku 5.5 · medium

      Clicks through a changed screen on the local dev server and screenshots it at phone and desktop width. Evidence, not proof.

      localhost only
    • scout Haiku 5.5 · medium

      Answers one lookup question, with file and line evidence. Keeps reviewers for real reviews.

      read-only

    No helper can start another helper. A guard checks every launch against one table of allowed models: Claude's built-in helpers, a wrong model or effort above xhigh are blocked.

    05

    Safety, strongest first

    Walls hold even if every agent misbehaves. Speed bumps catch honest mistakes. Written rules set the intent.

    1. Wall

      Branch protection on main

      Changes reach main only through a pull request with green checks. The bypass list is empty, so the rules also bind the owner's own login, which the agents use.

    2. Wall

      No production secrets on the machine

      Local env files hold fake values. Real keys live outside the project.

    3. Speed bump

      Helper guard

      A hook checks every helper launch against one table of allowed models, before the helper starts. A wrong model, a built-in helper or effort above xhigh is blocked, with a message saying what's allowed. Effort max, Opus on the wide implementer and Fable show you a pop-up.

    4. Speed bump

      Deny rules

      They block pushing to main, merging, reading secrets, migrations and the production scripts folder, also when git is pointed at another folder with -C. They match command text, which is why the walls exist.

    5. Speed bump

      Ask rules

      A pop-up appears before installs, web access and edits to the rule files. Tested finding: they work for tools, but they don't stop a helper from starting.

    6. Written rule

      The playbook

      Fable and max effort only after a yes in chat, then on the pop-up. Nothing runs outside the approved plan. Anything unclear means stop and report.

    06

    How it runs: files and sessions

    Start line

    You're the orchestrator. Read ORCHESTRATOR.md, then the Now section of PLAN.md, and report.

    • The Now block in PLAN.md is updated at every stage, with the goal and your decisions written down as you make them, so any fresh session can pick up where the last one stopped.
    • Start a fresh session after a merge once the conversation passes about 250k tokens.
    • As a safety net, the template sets auto-compaction to 400k; on 1M-context models it would otherwise wait until about 967k.
    • Every reply follows one of five fixed shapes (an output style), from the first message of every session.
    • When a session starts and after any compaction, a hook prints the Now block into the conversation, so the current state is never lost.
    • A helper's cache lasts only 5 minutes. Resume a helper within that window; otherwise start a fresh one with a short brief that includes the first helper's handoff line: what it tried, what didn't work, what it would do next.

    07

    Lessons from real use

    What each version changed, and why. The full list is in the changelog.

    1. v1.3Oct 2026
      • Hard limits: one table says which models each helper may use, and a guard hook enforces it before every launch. Effort stops at xhigh unless you say yes to max, in chat and then on a pop-up. A written limit is a wish; a hook is a limit.
    2. v1.2Oct 2026
      • Auto-compaction moves to 400k and sessions rotate after about 250k. Now carries the goal and your decisions: with them, a fresh session recalled 9 of 9 facts, without them 8.
      • An upgrade prompt applies only the changes between two versions, so your adapted rules stay.
      • Install with one line. A new-project path creates the repo, a skeleton, one test and CI first, so branch protection has a check to require.
      • Optional parallel packages: big tasks that share no files can run at the same time in separate worktrees. Off by default; it saves time, not tokens.
      • A new ui-tester (Haiku 5.5) clicks through screen changes on localhost and screenshots them. The proof stays the end-to-end tests in CI.
      • Helpers commit before reporting and add a handoff line, so a fresh helper can pick up both the work and the reasoning.
      • Plan review stops after three rounds at most, and review findings need evidence before they send work back.
      • The scout moves to Haiku 5.5: 10 of 10 lookups right, same as Sonnet, at about 1/13 of the cost.
      • An output style gives the orchestrator five fixed reply shapes, so every new session answers the same way.
      • A helper costs about 11–12k tokens to start (measured), not 20k.
      • Git runs as git -C <folder>. Claude Code now asks before cd + git, and a separate cd made git run in the wrong repo.
    3. v1.1Oct 2026
      • On 1M-context models auto-compaction only starts at about 967k tokens, so the template sets it to about 600k as a safety net.
      • A hook prints the plan's Now block right after a compaction, so the state comes straight back.
      • A helper's prompt cache lasts 5 minutes, so a helper resumed later pays for its whole history again. Resume quickly, or start fresh.
      • Claude Code Projects now covers part of this ground. It suits self-contained repos and cloud work; this template stays for local work and a per-helper model split.
    4. v1.0Oct 2026
      • A cheap, read-only scout takes simple lookups, so reviewers only do real reviews.
      • You decide four kinds of thing: wording, product behaviour, production and money, scope. The orchestrator decides the rest and logs it.
      • Ask rules don't stop helpers from starting, so Fable's gate is a written rule plus a log.
      • Feature branches are created with --no-track, so a push can never aim at main.
      • New tests are judged against main, also in fix rounds.
      • Each helper costs tokens just to start (measured at about 11–12k in v1.2), so small tasks are grouped.

    08

    Install

    Open Claude Code in the folder that contains your project, or an empty folder for a new one, and type:

    Install the Claude Code Orchestrator v1.2 here: clone https://github.com/bn-basel/claude-code-orchestrator at tag v1.2 next to this folder, then follow its INSTALL-PROMPT.md.

    It clones the repo at a fixed version and follows INSTALL-PROMPT.md. No project yet? It creates the GitHub repo, a skeleton with one test and a CI check first.

    Later, UPGRADE-PROMPT.md moves you to a newer version: it applies only the changes between versions, one by one with your yes, and keeps your own rules.

    Or use Claude Code Projects

    Projects (public beta on Pro and Max) is Claude Code's built-in version of the same idea: one coordinator conversation, one thread per task, shared instructions and memory, and threads that run in the cloud by default.

    • Projects fitsA self-contained GitHub repo, and work you're happy to run in the cloud.
    • This orchestrator fitsLocal work and a different model per helper. Projects can't adopt a local session, gives every thread the same model (all Opus uses plan limits faster), and is still a beta.
